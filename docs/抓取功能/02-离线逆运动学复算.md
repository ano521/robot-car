# 离线逆运动学复算（没碰车、没动机械臂）

生成时间：2026-10-25
方法：把 `src/yolov8_ros/script/z_kinematics.py` 的 `kinematics_analysis()` / `kinematics_move()`
**逐行复刻**成独立脚本，在 PC 上跑。除了「把文件读进来」以外，和车上任何东西都没关系。
脚本：`脚本/kin_check.py`、`脚本/kin_check2.py`（可以自己再跑一遍复核）

> 为什么要先做这一步：机械臂一动就是"真金白银 + 可能撞坏"，而**运动学是纯数学**，
> 完全可以在插上电之前先算清楚。上车前的每一个"我以为是"都要先在这里换成数字。

---

## 一、复刻的模型（这就是代码里的事实）

```
L0/L1/L2/L3 = 100/105/75/185  (mm)    ← grab.py:244、put.py:238、keyboard_grasp.py:193
             setup_kinematics 里各 ×10  →  1000/1050/750/1850 (0.1mm)
kinematics_analysis(x,y,z,Alpha)       ← x,y,z 再 ×10，Alpha 是"爪子与水平面的夹角"
   theta6 = atan(x/y)                  ← 云台（底座旋转）
   y' = hypot(x,y) - L3·cos(Alpha)
   z' = z - L0 - L3·sin(Alpha)
   解 2 连杆 (L1,L2)  ->  theta5, theta4, theta3
   七个 return 1..7 就是七种"不可达/越界"
PWM = 1500 ∓ 2000·angle/270            ← 中位 1500，270° 对应 ±2000 tick（1° ≈ 7.41 tick）
```

`kinematics_move(x,y,z,t)` 的选角策略（`grab.py:215`、`z_kinematics.py:120`）：
**在 alpha ∈ [-135, -1) 里找"最负的可行值"**。

## 二、结论 1：厂商标定那四个点在几何上是自洽的 ✅

厂商给的标定框（`grab.py:76-79`）：像素 `(187,362)↔(-88,170)`、`(492,119)↔(110,260)` mm。
把它四个角分别按 grab / put 的真实下发方式算一遍：

| 目标 | 机械臂坐标 | 可达 | 选中 alpha | PWM [0,1,2,3] |
|---|---|---|---|---|
| 左下角 抓取 | (-88, 190, z=10) | ✅ | -72 | 1684, 1137, 1707, 869 |
| 左下角 抓取(dx=-6) | (-94, 190, z=10) | ✅ | -72 | 1694, 1113, 1655, 842 |
| 左下角 放置 | (-88, 184, z=25) | ✅ | -71 | 1689, 1175, 1702, 834 |
| 左下角 放置抬臂 | (-88, 184, z=200) | ✅ | -23 | 1689, 1497, 1691, 857 |
| 右上角 抓取 | (110, 280, z=10) | ✅ | -46 | 1341, 995, 1640, 1137 |
| 右上角 抓取(dx=-6) | (104, 280, z=10) | ✅ | -47 | 1349, 990, 1615, 1110 |
| 右上角 放置 | (110, 274, z=25) | ✅ | -47 | 1337, 1005, 1563, 1043 |
| 右上角 放置抬臂 | (110, 274, z=200) | ✅ | -12 | 1337, 1232, 1561, 1073 |
| 中心 抓取 | (11, 235, z=10) | ✅ | -66 | 1480, 1074, 1612, 882 |
| 中心 放置 | (11, 229, z=25) | ✅ | -65 | 1479, 1129, 1651, 873 |

**结论**
1. 全部可达，**PWM 全在 [500,2500] 安全区间内**，没有任何一个越界。
2. ⇒ **运动学本身不是瓶颈**。抓不到东西，问题不在"算不出来"，而在
   "算出来的点是不是真的那个点"（标定 G6/G7/G8）、"夹爪到底合没合上"（G9）、
   "舵机走没走到"（G13）。
3. 顺带得到两个可用于现场核对的基准值：
   - 抓左下角 时 1 号舵机 ≈ **1137**、2 号 ≈ **1707**、3 号 ≈ **869**
   - 抓右上角 时 1 号舵机 ≈ **995**、2 号 ≈ **1640**、3 号 ≈ **1137**
   上机手动试舵机时，如果发给舵机的 PWM 和这两个数差很多，说明**参数或标定被改过**。

## 三、结论 2：L0 的 100 / 110 之争不是小事 ⚠️

`grab.py`/`put.py`/`keyboard_grasp.py` 用 L0=100，`arm_move.py` 用 L0=110。
同一个目标 `(0, 200, z=10)`：

| L0 | alpha | PWM |
|---|---|---|
| 100 | -74 | 1500, **1159**, 1741, 867 |
| 110 | -76 | 1500, **1123**, 1715, 861 |

**1 号舵机差 36 tick ≈ 4.9°**，末端在 200 mm 处约差 **1.7 cm**。
要抓 3 cm 的木块，这个量**不能忽略** —— 而且它是"系统性偏移"，
不会时好时坏，表现是"每次都偏同一侧"，很容易被误判成"相机装歪了"。

**处理**：拿尺子量真的 L0（底盘面 → 2 号舵机中心轴），定死一个值写进公共配置。

## 四、结论 3：几何可达范围几乎是"全绿"，所以危险不在"够不着" 🟡

- 原因是 `L3 = 185 mm` 这根"前臂"很长，`y' = hypot(x,y) - L3·cos(alpha)` 把大部分距离吃掉了。

- 安全只能靠：**限幅**（代码里卡 ±150 mm / y ≥ 80）、**限速**（`T` 参数别小于 1000 ms）、
  和**人不在臂展范围内**。

## 五、结论 4：选角策略跟它自己的注释相反 🟡

- 注释（`z_kinematics.py:36`）："Alpha 为爪子和平面的夹角 **-25 ~ -65 范围比较好**"。
- 代码：取可行集里**最负**的那个 → 实测落到 **-46 ~ -74**。

抓桌面上的东西时"越陡越好"未必是坏事，但**货架抓取（有层板）时陡姿态更容易撞层板**。
建议：加一个"期望 alpha"参数（默认 -45），在可行集里选**最接近**它的，而不是无脑取极值。
——这条改动很小，但会让货架抓取从"看运气"变成"可控"。

## 六、结论 5：`grab.py` 里两套像素→机械臂换算差多少 🟠

`grab.py` 同一个像素点算了两遍，**两遍结果不一样**，而且两套都被用了
（第一套算云台角，第二套算手臂位置）：

| 像素 | 第一套 `kms_x,kms_y`（`:66-67`） | 第二套 `X_mc,Y_mc`（`:87-90`） | 分歧 |
|---|---|---|---|
| (320,240) 画面正中 | (18.75, 180.00) | (-1.7, 215.2) | **20.5 mm / 35.2 mm** |
| (187,362) 标定框左下 | (-31.12, 134.25) | (-88.0, 170.0) | 56.9 mm / 35.8 mm |
| (492,119) 标定框右上 | (83.25, 225.38) | (110.0, 260.0) | 26.8 mm / 34.6 mm |

**注意最后两行**：在**标定框的两个角上**，两套换算都差 3~6 cm。
也就是说"标定"这件事只在它自己被用的那一套里成立 —— 云台角用的是**完全没标定过**的线性公式。

**⇒ 臂伸到位了，云台却按另一个方向转 → 末端必然偏。这是 G7 的量化证据。**

补充：第一套换算里 `theta6` 的实际范围只有 **-31° ~ +30°**（对应云台 PWM **1274 ~ 1729**），
不是满量程 ±90°。因为 `kms_y` 最小只到 90 mm（`c_y=480` 时）。

## 七、结论 6：标定框外的目标会被"静默钳位" 🟡

`np.interp` 对区间外的输入直接取端点，不报错：

| 像素 x | 得到 X_mc | 说明 |
|---|---|---|
| 0 / 100 | -88.0 | 框是 187..492，左边一律钳到 -88 |
| 600 / 640 | +110.0 | 右边一律钳到 +110 |

`y` 同理（0/50 → 260；400/480 → 170）。

⇒ 目标出现在画面边缘（车没停准、货架偏高/偏低时很常见）时，
机械臂会**认认真真奔向一个极限位置**，日志一切正常，然后抓空。
**必须在调用前加范围检查，越界就放弃并打 `logwarn`。**

## 八、结论 7：`theta6 = atan(kms_x/kms_y)` 的 0/0 洞 🟢（低危）

`grab.py:99`。只有 `kms_x==0 且 kms_y==0` 才会踩到 `ZeroDivisionError`，
而 `kms_y = 0` 需要 `c_y = 720`（画面只到 480）⇒ **实际到不了**。记一笔，不修也行。
