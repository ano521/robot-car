## 0. 一句话结论

> 抓取链路**不是"差一点调通"，而是至少有 1 个必坏点、2 个未知的致命点、3 个没验证过的假设**。
> 现在直接按 `grasp.sh` 第 7 页那个 `1`，最可能的结果不是"抓不到"，
> 而是**机器人走到第一个抓取点就永远停在那儿，不动、不报错、不退出**。

必坏点（🟥）：**YOLO 订阅的相机话题，和相机实际发布的话题不是一个**（G1）。
致命未知（⬜）：**`/dev/arm` 这个机械臂串口在不在**（G2）—— 不在的话 `grab.py` 连 import 完都活不过一行。

**夹爪"合上"到底是 P2100 还是 P1700**（G9）。

## 3. 断点清单

严重度：🔴 阻塞（不改就跑不通） / 🟠 高风险（能跑但结果不可信） / 🟡 待确认

### G1 · YOLO 订阅的相机话题 ≠ 相机发布的话题 🔴🟥

- **证据**
  - 相机：`usb_cam.launch:2` 节点名 `usb_cam2` → 图像落在 `/usb_cam2/image_raw`（`:32` 又 remap 了一次同样的名字）。
  - YOLO：`multi_yolo.py:14` 订阅 **绝对话题** `/usb_cam/image_raw`。
  - `grasp.sh` 一共 8 个标签页，**没有任何一个**会发 `/usb_cam/image_raw`（那是 `cam_track` 的 video0，只在 `3-amcl_test.sh` 里起）。
- **后果**：`multi_yolo.py` 永远收不到图 → `/yolov8_detections` 一条都不会有 →
  `grab.py` 永远等不到 `class_name == "car"` → `/success` 永远是 False →
  **`nav.py` 卡在第 233 行的 `while True` 里，机器人停在第一个抓取点，屏幕上一片正常**。
  这正好解释了"为什么从没人见它真的抓过东西"。
- **为什么之前没发现**：B1 那次验证的是"RViz 有没有画面"，RViz 订阅的确实是 `/usb_cam2/image_raw`
  —— **画面出来 ≠ YOLO 拿到图**。当时把"出图"当成了"视觉链路通"，跳过了中间这一环。
- **30 秒验证**（在 `grasp.sh` 起来的会话里，另开一个终端，先 `source ros-env.sh`）
  ```bash
  rosnode info /yolov8_ros_node | sed -n '/Subscriptions/,/Services/p'
  rostopic info /usb_cam/image_raw | grep -A2 Publishers     # 应显示 no publishers
  rostopic hz /yolov8_detections                             # 应长时间 no new messages
  ```
- **修法**（推荐改 launch，不动 py）：`multi_yolo.launch` 里给节点加一行 remap
  ```xml
  <node name="yolov8_ros_node" pkg="yolov8_ros" type="multi_yolo.py" output="screen">
    <remap from="/usb_cam/image_raw" to="/usb_cam2/image_raw"/>
  </node>
  ```
  这样 `sam` / `track` / `region_counter` / `vl_locate/server.py` 那几个同样订阅 `/usb_cam/image_raw`
  的包**不受影响**（它们本来就跟 video0 的 `cam_track` 配套）。
- **风险**：极低，只影响这一个节点。

### G2 · `/dev/arm` 到底存不存在 ⬜（最要紧的未知）

- **证据**：`WCXC_UartServer.py:19` 写死 `port='/dev/arm'`；`0-check.sh` 第 3 节只查
  `/dev/abot_driver`、`/dev/rplidar`；`killall.sh` 第 5 节的 `fuser` 兜底也只兜这两个。
  文档里 `/dev/arm` 从未出现，`ttyUSB2` 的角色也从未写明。
- **后果**：串口打不开 → `serial.Serial()` 抛 `SerialException` →
  `grab.py` 在 `__main__` 第 243 行就崩 → 进程退出（`grasp.sh` 那个标签页会看到红字）→
  `/success` 永远 False → 同 G1 的结局：卡在第一个点。
- **另一层风险（即使 `/dev/arm` 存在也一样中招）**：`grasp.sh` 同时起了 `grab.py` 和 `put.py`，
  两个都在 `__main__` 里 `WCXC_UART(115200)` —— 也就是**两个进程同时打开同一个 tty**。
  `pyserial` 默认**不加独占锁**（`exclusive=False`），所以两边都会"打开成功"，
  然后：写入交错在同一个舵机总线上；更要命的是**读**——两边各自持有一个 fd，
  舵机回的 `#...!` 应答会被**随机一个进程抢走**。
  后果：任何"读回角度做校验"的逻辑（G3 想加的那个）都会随机失败；
  现在的代码不读回，所以暂时看不出来，但这条路一直是悬着的。
- **正确姿势**：机械臂串口在**整台车上有且只能有一个属主**。要么合并成一个 `arm_bridge` 节点
  （`grab.py`/`put.py` 通过服务/话题请求动作），要么就把 `grab.py`、`put.py` 合成一个进程。
  这条比 G1 的影响面更大 —— 它决定了抓取功能的结构怎么搭。
- **验证**：`./7-grasp-check.sh`（第 1、2 节），或
  ```bash
  ls -l /dev/arm /dev/ttyUSB*
  sudo udevadm info -q property -n /dev/arm | grep -E 'ID_MODEL|ID_PATH'
  ```
- **修法**：不要动车内 udev（红线）。代码侧加一个**可覆盖的端口**：
  `port = os.environ.get('ABOT_ARM_PORT', '/dev/arm')`，现场用
  `export ABOT_ARM_PORT=/dev/ttyUSB2 ./7-...` 解决。这是最小改动。
- **⚠️ 这条比 G1 更该先查**：G1 我读代码就能断定，G2 只能上机。

### G3 · `success` 不是"抓到了"，是"动作发完了" 🟠🟥

- **证据**：`grab.py:193` 在 `carry_step==4` 的末尾**无条件** `rospy.set_param('success', True)`；
  `put.py:188` 同样。全程没有：夹爪电流、舵机位置回读、视觉二次确认。
- **后果**：抓空了、抓歪了、目标压根不在框里 —— **全都报成功**。
  这种"全流程绿灯但什么也没抓到"是最难查的一类问题，而且会把
  导航点位、手眼标定、夹爪行程三件事混在一起。
- **修法（分两级）**
  1. 便宜版：加**视觉二次确认** —— 抓取抬起后再看一帧，目标类别是否还在原位（bbox 是否消失/位移）。
  2. 可靠版：舵机位置回读。协议本身支持 —— `arm_move.py:32-78` 已经在用
     `#000PRAD!` 读角度了，抓取后用同样方式读 `#005PRAD!`（夹爪）判断是否"夹到了东西"
     （夹空时闭合角度会和夹住时不同）。这需要先实测两个角度值。
- **风险**：低成本、高收益，建议做。

### G4 · `nav.py` 等 `/success` 是死等，没有超时 🟠🟥

- **证据**：`nav.py:233-239`（以及 247、262、274、288、301 共 6 处同样的 `while True`）。
- **后果**：G1/G2 任一环坏 → 机器人不动、不报错、不退出。**现场最难判断"它到底在干嘛"**。
- **修法**：加超时（如 60 s）+ 失败日志 + 明确的失败策略（跳过该点 / 中止并停车）。
  不要用 `while True`。

### G5 · 抓取类别被写死成 car → clock → person 🟠🟥

- **证据**：`grab.py:39` `label=["car","clock","person"]`、`:46` `msg.class_name==label[i]`；
  `i` 只在 `carry_step==4` 尾部 `i += 1`（`:197`）。`put.py` 同样。
- **后果**
  - 第 1 个货架必须是 **car**，第 2 个 **clock**，第 3 个 **person**，否则永远不触发；
  - 抓失败一次 `i` 不增 → **后面全部错位**；
  - 而且 COCO 里的 `car` / `clock` / `person` 都是"实物大物体"，我们桌上摆的多半不是这些。
- **修法**：改成"参数化目标类别列表"（`rosparam` 可配），或者干脆不按类别过滤、
  改按"离画面中心最近的检测框"选目标。后者更稳，也不依赖 COCO 有无对应类。

### G6 · 手眼标定是厂商机位量出来的 4 个点 ⬜🟠

- **证据**：`grab.py:76-79`
  ```python
  cali_1_im = [187, 362]; cali_1_mc = [-88, 170]
  cali_2_im = [492, 119]; cali_2_mc = [110, 260]
  ```
  只有两个点（一左下一右上）做**线性插值**，没有畸变、没有深度、没有相机外参。
- **判断**：这套参数只有在"相机怎么装、臂怎么装、桌面多高"和厂商完全一致时才成立。
  我们已经换过房间、动过相机（`sudo reboot` + mjpeg），**没有任何证据表明这四个点还成立**。
- **我需要知道的**：这台车的相机是装在**机械臂/底盘正前方**还是**侧上方**？
  从代码看是"臂在画面下方、目标在画面上方"，`kms_y` 由像素 y 线性映射到 90~270 mm。
- **修法**：做一个**现场标定工具**：把目标物放在桌面上 6~9 个已知位置，
  记录像素坐标 + 臂实际能抓到的 (x,y)，拟合出我们自己的映射（甚至可以直接拟合
  像素→舵机 PWM 的仿射变换，绕过 mm 坐标这一层，少一层误差）。

### G7 · 同一个文件里有两套"像素→机械臂"换算，结果不一致 🟡🟥

- **证据**：`grab.py:66-70` 用 `(c_x-320+50)*30/80` 与 `180-(c_y-240)*30/80` 得到 `kms_x/kms_y`；
  `:87-90` 又用 4 点 `np.interp` 得到 `X_mc/Y_mc`。
- **后果**：`kms_x/kms_y` 只用来算**云台舵机角度 `theta6`**（`:99`），`X_mc/Y_mc` 用来算**手臂位置**。
  两套换算来自同一个像素点，但比例/偏移完全不同 →
  **手臂伸到 A 处，云台却按 B 处的方向转**，末端必然偏。
- **修法**：统一成一套。要么云台角也从 `(X_mc,Y_mc)` 反算 `atan2`，要么反过来。

### G8 · `np.interp` 越界静默钳位 🟡🟥

- **证据**：`grab.py:87-90`，标定框是 `x∈[187,492]`、`y∈[119,362]`。
  `np.interp` 对区间外的输入**钳到端点**，不报错。
- **后果**：目标出现在画面边缘（很常见，车没停准时）→ 手臂直奔极限位置 →
  "动了但没抓到"，而日志里一切正常。
- **修法**：加范围检查，越界直接放弃本次 + 打日志（`logwarn`），让上层知道"这次没抓"。

### G11 · 选 `alpha` 的策略和注释相反 🟡

- **证据**：`z_kinematics.py:36` 注释写"Alpha 为爪子和平面的夹角 -25~-65 范围比较好"，
  但 `grab.py:215-219` 和 `z_kinematics.py:120-127` 都是取**最负**的可行值（`min`）。
- **后果**：实测取到 -46 ~ -74，姿态比设计意图更陡。陡姿态对"从上往下抓桌面物"不一定是坏事，
  但**和注释意图相反**，且可能与货架层板干涉（货架抓取时尤其危险）。
- **修法**：加一个"期望 alpha"参数（默认 -45），在可行集里选**最接近**它的那个，
  而不是无脑取极值。这个改动对货架抓取是必要的。

### G13 · 所有动作都是开环 `time.sleep` 🟠🟥

`grab.py:152,157,172,177,186,190-192` 全靠 sleep 1~3 秒猜"舵机走完了"。
电池电压掉一点、舵机负载大一点，实际到位时间就变 → 抓取成功率随电量漂。
**这是"时好时坏"最常见的原因**，也是现场最难复现的。

### G14 · 抓/放之后立刻盲退 0.27 m 🟠

`nav.py:241,254,269,281,296` —— `end()` 是 `-0.3 m/s × 0.9 s`，**不看传感器**（`nav.py:70-82`）。
夹着东西往后倒，如果抓取位背后有货架/墙，就是撞。
**量点位时必须给抓取位背后留 ≥0.5 m**（点位表现在是按"设计"留的，但没实测过退路）。

### G15 · `theta6 = atan(kms_x/kms_y)` 未防 0/0 🟢

`grab.py:99`。当 `kms_x==0 且 kms_y==0` 时 `x==0 and y!=0` 不成立、另两个 elif 也不成立 → 走 else → `ZeroDivisionError`。
按 `kms_y_c = 180-(c_y-240)*0.375` 反推，需要 `c_y=720`（画面 480 高），**实际到不了**，
所以是"理论上的洞"，记一笔即可。

### G16 · `vl_locate` 那条 VLM 链路跟 `nav.py` 握手方式不兼容 🟡

`vl_locate/scripts/vision_arm.py:191` 用 **话题** `/success`（`std_msgs/String`）通知完成，
而 `nav.py:234` 读的是 **参数** `/success`。两条线接不起来。
另外 `vl_locate` 全线（`server.py:36`、`vision_arm.py`）也订阅 `/usb_cam/image_raw` → 同 G1。
要单独验证，不要和 YOLO 那条混着调。

### G17 · 8 秒去抖会把重试请求"吃掉"而不留痕 🟡🟥

- **证据**：`grab.py:61` 的时间闸 `if now - systick_ms_bak > next_time`，
  而 `next_time` 在 `:135` 被改成 **8000**（8 秒）。
  闸门不通过时函数直接 `return`，**但 `pose_callback`（`:53`）照样把 `/grab` 置回 False**。
- **后果**：抓取后 8 秒内再发一次 `/grab`（调试时极其常见），请求被**静默吞掉**，
  上层只会看到"没反应"，等 `/success` 等到天荒地老。
- **修法**：闸门不通过时**不要**清 `/grab`，或者干脆用"上升沿 + 完成回执"重写这段。
