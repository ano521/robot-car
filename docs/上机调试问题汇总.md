### B. 相机

#### B1 · RViz 里 `Image: No Image`，没有画面 —— **已查清，不是设备号问题**

**2026-10-10 22:0x 实测（`v4l2-ctl --list-devices`）：车上有两台 USB 摄像头，不是一台。**

```
HD USB Camera      (usb-3610000.xhci-2.1)  →  /dev/video0, /dev/video1
Integrated Webcam_HD (usb-3610000.xhci-2.3) →  /dev/video2, /dev/video3
```

| 设备号 | 名字 | 物理设备 |
|---|---|---|
| `/dev/video0` | HD USB Camera | 摄像头 **A**（USB 口 2.1） |
| `/dev/video1` | HD USB Camera | 同上，**A 的第二个节点** |
| `/dev/video2` | Integrated Webcam_HD | 摄像头 **B**（USB 口 2.3） |
| `/dev/video3` | Integrated Webcam_HD | 同上，**B 的第二个节点** |

**关键结论：摄像头每个会出两个 `videoN` 节点，第二个通常是元数据通道，不能当普通摄像头打开。
所以真正可用的是 `/dev/video0` 和 `/dev/video2`。**

⇒ `cam_track` 用 `video0`、`yolov8_ros` 用 `video2`，**两边其实都对**——它们指的是两台不同的相机。
**原先"设备号不一致是 bug"的判断（D5）作废。**

- **B1 的真正原因待定**：RViz 里 `Image: No Image` 可能是
  (a) `3-amcl_test.sh` 起的 `usb_cam` 节点话题名与 RViz 里配的 `Image Topic` 不匹配；
  (b) 该相机没被正确打开（被另一进程占用）；
  (c) RViz 配置里压根没设 topic。**下一步：`rostopic list` 找 `/usb_cam/image_raw` 是否存在。**
- **遗留问题**：还不知道 A / B 哪一台是机器人真正用来做视觉的那台（哪台拍得到桌面/机械臂前方）。需实拍确认。

  ps:     58745  1419  Mon Oct 12 14:51:42  abot  Ssl+  .../devel/lib/abot_bringup/abot_driver

  `STAT=Ssl+`（`S`=正常可中断睡眠，**不是**卡死的 `D`）⇒ **`kill -9` 一定杀得掉**。

  代码走的是 `else` 分支打 `ROS_INFO("read err %d", len)`（第 119 行）——
  而"没数据"走的是 `select` 超时分支，**根本不打日志**。所以满屏 `read err 0`

#### C7 · `/dev/ttyUSB*` 消失，`/dev/abot_driver`、`/dev/rplidar` 变成悬空软链接（2026-10-12 下午发现）

- **现象一**：`/rplidarNode` 没起来。`abot_bringup.launch` ⇒ `bringup.launch` +
  `model.launch` + `rplidar.launch`，雷达节点**本应**被拉起来，所以它的缺席是真故障。
- **现象二**：`abot_driver` 无限刷 `read err 0`（见 C6）。
- **现象三**：脚本里的自检被骗过去了 ——
  ```
  $ ls -l /dev/abot_driver
  lrwxrwxrwx ... /dev/abot_driver -> ttyUSB1     ← 看着一切正常
  ```
  **但 `ttyUSB1` 根本不存在。** 软链接创建于 14:15（udev 规则跑过），
  之后 `/dev/ttyUSB*` 消失了，软链接就成了**悬空链接**。
  ⚠️ **教训（已写进脚本）**：`[ -L "$d" ]` 对**悬空**软链接同样为真，
  `readlink -f` 还会把不存在的目标原样打出来 —— 于是旧版 `0-check.sh` 打印了 `[OK]`。
  必须**先测 `-e`**（会跟随软链接）再测 `-L`。`0-check.sh` 第 3 节与 `killall.sh`
  的"串口/设备节点"节都已按这个顺序重写。
- **15:23 `lsusb` 实测 —— 硬件其实在总线上**（这一点很关键，推翻了我先前的措辞）：

  | 总线 | ID | 说明 |
  |---|---|---|
  | 001 | `0403:6001` | FTDI **FT232 Serial (UART)** |
  | 001 | `10c4:ea60` | Silicon Labs **CP210x UART Bridge** |
  | 001 | `1a86:7523` | QinHeng **HL-340 / CH340 USB-Serial** |

  **三个串口芯片都在**（早上体检时 `/dev/ttyUSB0/1/2` 也正好是三个，与之一致）。
  ⇒ **排除**"USB 线掉了 / 适配器没供电 / 集线器死了"这一类**硬件**解释。
  故障在**驱动/设备节点这一层**：芯片挂在 USB 总线上，但没生成 `/dev/ttyUSB*`。
- **下一步（只读，不改任何东西）** —— 四条命令就能定性：
  ```bash
  ls -l /dev/ttyUSB* /dev/abot_driver /dev/rplidar   # ① 现在到底有没有
  ls /sys/bus/usb-serial/devices/                    # ② 驱动绑没绑上（空 = 没绑）
  dmesg | grep -iE "ttyUSB|cp210x|ch341|ftdi|brltty" | tail -40   # ③ 内核怎么说的
  dpkg -l | grep -i brltty                           # ④ 头号嫌疑犯在不在
  ```
  - **①有 `ttyUSB*`** ⇒ 已经自己恢复了（重新枚举成功），直接重跑 `1-gmapping.sh` 验证。
  - **①没有 + ②是空的 + ③里出现 `brltty`** ⇒ 就是 **brltty 抢占**（见下）。
  - **①没有 + ②有内容** ⇒ tty 在但别名/权限问题，另查。
- **头号嫌疑：`brltty` 抢占串口芯片。** Ubuntu 22.04 的一个著名坑：`brltty`（盲文点显器）
  的 udev 规则把一批 **USB 转串口芯片**误认成盲文设备抢走，**刚好覆盖**上面查到的三家
  （FTDI `0403:*`、Silicon Labs `10c4:ea60`、QinHeng `1a86:7523`），
  表现就是**`lsusb` 看得见、`/dev/ttyUSB*` 不出来** —— 与本次现象几乎逐字吻合。
  - **只读确认**：`ls /usr/lib/udev/rules.d/*brltty*`、`dmesg | grep -i brltty`
  - **临时验证**（不改任何文件，重启即失效）：`sudo systemctl stop brltty-udev.service`
    然后**重新插拔**对应 USB，看 `/dev/ttyUSB*` 是否出现。
  - ⚠️ **根治**（`sudo apt remove brltty`）属于**车内系统改动**，
    **超出"只动 U 盘"的既定范围** —— 动手前先跟用户确认。
- **零风险的第一招仍然是重启**：`sudo reboot` 后驱动会干净地重新绑定。
  顺序建议：先跑上面 ①②③④ 留证据 → 再重启 → `ls -l /dev/ttyUSB* /dev/abot_driver /dev/rplidar`。
- **✅ 15:31 复查：设备全回来了，属「瞬时掉线」不是「坏了」** ——

  ```
  /dev/ttyUSB0   crw-rw----  root dialout  188,0   10月12 15:12
  /dev/ttyUSB1   crw-rw----  root dialout  188,1   10月12 15:29   ← 底盘这个刚重建
  /dev/ttyUSB2   crw-rw----  root dialout  188,2   10月12 14:39
  /sys/bus/usb-serial/devices/  ->  ttyUSB0  ttyUSB1  ttyUSB2      ← 驱动全绑上了
  ```

  三个都是**真实的字符设备**（不是悬空链接），三个驱动端口也都绑上了。
  14:15 建的 `/dev/abot_driver -> ttyUSB1` 现在指向真实设备，**不再悬空**。
  `ttyUSB1` 的节点时间戳是 **15:29**（另两个分别是 15:12 / 14:39）——
  ⇒ **底盘那个适配器中途掉过，刚刚才重新枚举回来**。
- **⚠️ 关键：设备回来了，旧进程不会自愈。** 掉线时 `abot_driver` 手里握的是
  **旧 ttyUSB1 的 fd**（已 hangup）；重新枚举出来的是**新节点**，老进程还在读那个死 fd，
  `read err 0` 会一直刷下去。⇒ **必须 `kill -9` 掉再重启，不能指望它自己恢复。**
  这也再次印证 C6 的判读：它不是"占着串口"，是"攥着一个已经不存在的 fd"。
- **brltty 确实装着**（`ii brltty 6.0+dfsg-4ubuntu6`，附带 `libbrlapi0.7` / `python3-brlapi`），
  但**这次它没抢** —— 真被抢走的话 `/dev/ttyUSB*` 根本不会出现。

  留两条只读命令备用：

  systemctl list-units | grep -i brltty   # 服务在不在跑

  想知道"为什么会掉"只能 `sudo dmesg`（只读，安全）：
  ```bash
  sudo dmesg | grep -iE "ttyUSB|cp210x|ch341|ftdi|disconnect" | tail -60
  ```
- **权限**：设备是 `crw-rw---- root dialout`，能开的前提是用户在 `dialout` 组里。
  早上能跑说明多半没问题，顺手一查即可：`groups | grep dialout`。
